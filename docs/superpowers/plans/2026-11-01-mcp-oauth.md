# MCP Server with OAuth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an OAuth 2.1–protected MCP endpoint at `/api/mcp` so staff can let Claude, ChatGPT and other agents manage their sites and Mini CRM, with consent, revocation and an audit trail in the panel.

**Architecture:** A hand-rolled, narrow-profile OAuth authorisation server (`src/oauth/`) issues opaque, hashed, `token_version`-bound tokens. A fail-closed request pipeline (`src/mcp/`) runs Origin/Host → bearer → envelope → eligibility → scope before handing the request to the v2 MCP SDK's `createMcpHandler`. A central tool wrapper re-checks authorisation, allowlists the output and writes the audit log, then calls the existing services. The dashboard gets a consent page, Connected apps and an AI-agents settings page.

**Tech Stack:** Express 4, TypeScript, better-sqlite3, zod 4, vitest, `@modelcontextprotocol/server` v2 beta (exact pin), React 19 + shadcn/Tailwind.

**Spec:** `docs/superpowers/specs/2026-11-01-mcp-oauth-design.md`. Read it before starting any task; this plan cites its section names in *italics*.

## Global Constraints

- Feature flag `mcp`: admin-only, **off by default**. When off, `/api/mcp`, `/api/oauth/*` and the well-known endpoints answer **404**.
- MCP URL is `${PUBLIC_URL}/api/mcp` (no trailing slash); `issuer = PUBLIC_URL` origin (no trailing slash).
- Tokens are opaque: `wplmcp_at_` + 32 random bytes base64url (access), `wplmcp_rt_` + same (refresh). Only SHA-256 hex hashes are stored, and plaintext tokens are never logged.
- TTLs: authorisation code **60 s**, access **1 h**, refresh **30 days**, rotating on every use. Refresh reuse revokes the grant (strict, no grace window).
- PKCE **S256 only**; `plain` is refused. Redirect URIs must match exactly; `https` is required except for loopback (`http://127.0.0.1:*`, `http://localhost:*`).
- Scopes (exact strings): `sites:read`, `sites:write`, `crm:read`, `crm:write`, `invoices:write`, `admin:read`, `admin:write`. Read scopes: `sites:read crm:read`.
- Only verified users with role `owner` or `admin` may authorise or use MCP; the role is read from the DB on every call.
- Site reach is **owner-only**: no admin override, no shared-site access. Another user's site answers "Site not found".
- Invoice transitions allowed for agents: `draft → sent`, and `draft | sent | overdue → cancelled`. Nothing else.
- Protocol versions: `2026-07-28` (primary), `2025-11-25`, `2025-06-18`. Anything older is rejected.
- SDK packages are exact-pinned (no `^`). An SDK upgrade reruns all of Stage 1.
- UI: Tailwind tokens and shadcn primitives only; no hex values, no inline `style` (CLAUDE.md *CSS Architecture*).
- DB timestamps are stored as UTC `datetime('now')` strings without `Z`; compare them in SQL, never against JS local time.
- Audit retention is **90 days**. DCR clients never authorised are pruned after **24 h**.
- Rate limits: register 10/hour/IP; token 60/15 min/IP; authorize-request and decision 30/15 min/IP; `/api/mcp` 300/15 min per grant; site writes 10/15 min per user (same as `siteWriteLimiter`); CRM and admin writes 60/15 min per user.
- New env var `MCP_ALLOWED_ORIGINS` (comma-separated, empty by default).
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **`PUBLIC_URL` with a trailing slash, a path, or an uppercase host.** The issuer, resource and well-known URLs must still be canonical, and a client's `resource=` that differs only by host case must be accepted. Pinned in Task 2 (`mcpUrls` tests) and Task 7 (`resource` comparison test).
2. **A user deleted while a grant is live.** The next MCP call must get 401 and the refresh must get `invalid_grant`, never a 500 from a null user. Pinned in Task 7.
3. **Hostile client metadata** (a 10 KB `client_name`, a `javascript:` or `http:` `logo_uri`, control characters). The name is stored truncated to 100 chars with control characters stripped, and the logo is kept only if it is `https:`. Pinned in Task 4 and the consent-page test in Task 18.
4. **Token expiry across time zones.** With `TZ=Asia/Karachi` set in the test, an access token 59 minutes old is valid and one 61 minutes old is not. Pinned in Task 7.
5. **Huge or deeply nested tool arguments** (a 900 KB message body, arrays of 10 000 items). The audit summary stays bounded: strings over 200 chars, arrays over 20 items, and depth beyond 4 are each replaced with a short placeholder. Pinned in Task 9.

  ```ts
  export function redeemCode(p: { code: string; client_id: string; redirect_uri: string; code_verifier: string; resource?: string }): TokenResponse;
  export function refresh(p: { refresh_token: string; client_id: string; resource?: string; scope?: string }): TokenResponse;
  export function revokeGrant(grantId: string): void;                 // stamps revoked_at; invalidates that client's pending codes for that user
  export function revokeAllForUser(userId: string): number;           // revokes grants + stamps invalidated_at on unredeemed codes
  export function revokeToken(rawToken: string): void;                // RFC 7009: revokes the token's grant; unknown token is a no-op
  export interface McpAuthContext { userId: string; userEmail: string; userRole: 'owner'|'admin'; grantId: string; clientId: string; clientName: string; scopes: Scope[] }
  export function validateAccessToken(raw: string, resource?: string): McpAuthContext | null;
  ```
- Behaviour is exactly as the spec's *Code-to-grant lifecycle* and *Refresh rotation*:
  - Each of `redeemCode` and `refresh` is **one `db.transaction`**.
  - `refresh` consumes the token with `UPDATE … SET rotated_at = datetime('now') WHERE token_hash = ? AND rotated_at IS NULL`. Zero changes means reuse: revoke the grant and throw `invalid_grant`.
  - Redemption replaces an existing un-revoked grant for the same (client, user) pair by revoking it.
  - A `refresh` may narrow `scope`, never widen it.
  - `validateAccessToken` reads the token, its grant, and the user **live**. It returns `null` when any of these hold: the token is unknown or expired; it is a refresh token; the grant is revoked; the version mismatches; the user is missing, unverified or not owner/admin; the `resource` doesn't match. It updates `last_used_at` at most once per minute.
